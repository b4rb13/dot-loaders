<section id="policy">

## Choose a style policy before enhancement [#policy]

`stylePolicy` is either `{mode:'external', href:'/dotquilt/region.css'}` or `{mode:'inline', nonce}`; plain inline mode can be authorized by exact CSS hashes. Pass the policy to every participating component, including placeholders and refresh indicators. Different families need their own matching public CSS file. Establish the policy before connection or registration installs styles; changing it later is a diagnostic, not a stylesheet migration.

The examples use application classes and an external `app.css`, with `style-src-attr 'none'`. A nonce authorizes matching style elements, not arbitrary style attributes. Do not add `unsafe-inline`, `unsafe-eval` or a blanket Trusted Types policy to hide violations. The sample response policies are complete for these small local apps; adapt allowed origins and other resources to your application and test the actual response headers.

The docs website is a separate app and does not claim to run under the example's strict policy. Open the standalone example to inspect that policy.

</section>

<section id="external">

## Serve the matching external assets [#external]

External mode is the simplest place to start. The included `styles.ts` copies the installed React package's public region and skeleton CSS assets into `public/dotquilt/`. Each native shadow root receives its matching link; the React adapter also renders static CSS links before enhancement. The application stylesheet is separate.

CSP must permit the stylesheet origin. A missing, blocked or HTML-replaced stylesheet must not be counted as an authorized surface. Pin assets to the same package artifact as the JavaScript; a similarly named file from another build is not equivalent. This docs slice preserves the frozen bytes and does not change CSP enforcement inside the engine.

</section>

<section id="nonces-hashes">

## Keep nonces fresh and hashes exact [#nonces-hashes]

Nonce mode generates an unpredictable value per document request and uses it in the enforced response header, server markup and later shadow styles. Never accept a visitor-provided nonce, cache nonce-bearing HTML across visitors or keep one value in global server state. Browsers hide the nonce attribute's string; use the standard `.nonce` property when a client must read its own authorized script.

Hash mode computes SHA-256 over exact exported CSS strings. The React example imports both native runtime and React static arrays from their public `/server` entries, including each emitted string and newline-joined form. Hashing only the server placeholder misses later native styles. Recompute from the installed artifact whenever it changes; do not copy hashes across versions or edit whitespace after hashing.

The hash example authorizes styles only. Its bootstrap script still has a fresh nonce. Next's streamed/bootstrap scripts need framework authorization even when Dotquilt uses external CSS; this guide does not claim a fully static Next CSP or SRI implementation. For request-time nonces and caching constraints see [Next's CSP reference](https://nextjs.org/docs/app/guides/content-security-policy).

</section>

<section id="document-lifetime">

## Keep the existing document policy on navigation [#document-lifetime]

An RSC response is not a new top-level document. The Next example captures its initial root-layout style policy in an application-owned client context and retains it through navigation. Later responses may have different nonces; those values do not replace the original document's enforced header. A full reload creates a fresh policy. Keep providers/custom animation functions in client modules and pass only serializable initial values through server boundaries.

Verify this with real client navigation after the native tags are already registered: new hosts must use the original document's nonce or external mode, while an independent full-page request receives a different nonce. Test concurrent requests and capture `securitypolicyviolation` events along with hydration errors. Browser tests supplement a deployment policy review; they do not prove that every allowed source or hosting configuration is secure.

</section>
